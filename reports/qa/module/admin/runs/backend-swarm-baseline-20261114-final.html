HIGHComplete Absence of Administrative Audit Logging for High-Privilege ActionsSECURITY_VULNERABILITYOPEN

backend/src/services/admin.service.js:55-220 · VERIFIED confidence: HIGH

Evidence

AdminService methods (updateUser, deleteUser, upsertSetting, deleteLead, createResource, updateResource, deleteResource, deleteCategory, deleteCourse, deleteVideo) execute destructive state mutations with zero audit logging. No AuditLog model, table, or write operation exists.

Scenario

A compromised admin account or rogue insider silently promotes test accounts to admin, deletes student accounts, wipes courses, or alters pricing. When discovered, no audit log exists to identify which admin credentials performed the actions, from what IP address, or at what timestamp.

Impact

Violates non-repudiation, OWASP ASVS Section 7, and SOC2/ISO 27001 compliance standards. Forensic investigation after a breach or unauthorized data modification is impossible.

Reproduction

Perform PATCH /api/admin/users/:id with { role: 'admin' } or DELETE /api/admin/users/:id. Inspect MongoDB; no audit record is created.

Suggested remediation

Create an immutable AuditLog collection and service (recording actorAdminId, ip, userAgent, action, targetEntity, targetId, before, after, timestamp) and invoke it for all state-mutating admin endpoints.

Regression test

Execute mutation endpoints and verify an AuditLog record is persisted with matching admin ID, target ID, and action.

backend/src/services/admin.service.js:55-71 · VERIFIED confidence: HIGH

Evidence

static async updateUser(callerAdminId, targetUserId, data) { ... const { name, email, phone, company, role, interest } = data; const user = await User.findByIdAndUpdate(targetUserId, { $set: { name, email, phone, company, role, interest } }, { new: true, runValidators: true })

Scenario

Any user with 'admin' role can arbitrarily promote any customer to 'admin'. Furthermore, an admin can change the 'email' of any other admin without superadmin approval or password confirmation, enabling trivial account hijacking of peer administrators via password reset flows.

Impact

Full horizontal and vertical privilege escalation. Any compromised admin account can take over all other admin accounts and create unlimited new administrators.

Suggested remediation

Regression test

Attempt role escalation or email change on an admin account from a non-superadmin session; assert 403 Forbidden.

HIGHTOCTOU Race Condition in Last-Admin Protection Permitting Permanent Administrative LockoutIMPLEMENTATION_DEFECTOPEN

backend/src/services/admin.service.js:59-87 · VERIFIED confidence: HIGH

Evidence

In updateUser: if (data.role === 'customer') { const adminCount = await User.countDocuments({ role: 'admin' }); if (adminCount <= 1) throw new AppError('Cannot demote the last admin', 400, 'LAST_ADMIN') }
In deleteUser: if (targetUser.role === 'admin') { const adminCount = await User.countDocuments({ role: 'admin' }); if (adminCount <= 1) throw new AppError('Cannot delete the last admin', 400, 'LAST_ADMIN') }

Scenario

When exactly 2 admins exist, if Admin A demotes Admin B while Admin B demotes Admin A concurrently, both requests execute countDocuments simultaneously, both see count 2, and both proceed to demote the users. The system is left with zero administrators.

Impact

Complete administrative lockout from the application with no admins remaining to manage users, content, or system settings.

Reproduction

Issue concurrent PATCH /api/admin/users/:id demoting both admins simultaneously. Both requests succeed, leaving 0 admins in database.

Suggested remediation

Wrap the admin count check and demotion/deletion inside a MongoDB multi-document transaction with isolation, or use an atomic conditional query with optimistic concurrency control.

Regression test

Simulate simultaneous demotions using Promise.all; verify that at least one request fails with LAST_ADMIN and exactly one admin remains.

HIGHInconsistent Strike Management, Lack of Strike Reset, and Premature Playback UnlockingIMPLEMENTATION_DEFECTOPEN

backend/src/services/admin.service.js:182-220 · VERIFIED confidence: HIGH

Evidence

approveIncidentAndUnlockPlayback sets playbackLocked: false on User, but recordingStrikes is never decremented or reset. Furthermore, if a user has multiple pending incidents, approving one incident unlocks playback while other incidents remain pending_review. Also, neither approve nor ban validates incident.status !== 'pending_review', allowing state overwrites.

Scenario

A student receives false positive screen capture flags, accumulating recording strikes. Admin approves the incident, but strikes remain incremented forever. Additionally, an admin resolving an already banned incident unlocks playback for a banned account.

Impact

Students can be permanently penalized by false-positive strikes with no administrative mechanism to clear them. Multiple incident handling leads to race conditions bypassing security review.

Reproduction

Create user with 2 pending incidents. Call POST /api/admin/security-incidents/:id/resolve on incident 1. Observe User.playbackLocked becomes false while incident 2 is still pending_review. Observe recordingStrikes counter is not decremented.

Suggested remediation

1) Check for remaining pending_review incidents before clearing playbackLocked. 2) Provide explicit strike decrement/reset options. 3) Validate state transitions (incident.status === 'pending_review' required). 4) Add direct student strike management endpoint.

Regression test

Attempt to resolve an incident with status 'user_banned'; assert rejection with 400 INVALID_STATE_TRANSITION. Verify playback is not unlocked if other pending incidents exist.

backend/src/services/course.service.js:51-161 · VERIFIED confidence: HIGH

Evidence

CourseService.listCategoriesAdmin, listCoursesAdmin, and listVideosAdmin call Model.find().sort() with zero limit or pagination. AdminService listUsers, listLeads, and listPayments use hardcoded limit(500) with no page or offset query parameters.

Scenario

As LMS video, course, and user tables scale into thousands of records, admin dashboard listing triggers unindexed full collection scans and pulls entire datasets into Node.js heap memory, resulting in high event-loop blocking and Out-of-Memory (OOM) crashes.

Regression test

Call GET /api/admin/lms/videos?page=1&limit=20; assert response contains paginated items and totalCount metadata.

Scenario

Admin or compromised session submits invalid types or corrupted payloads to CMS resources (e.g. invalid plan prices or malformed partner URLs). The unvalidated settings are immediately broadcast to all connected clients via SSE.

Send invalid body to POST /api/admin/resources/plans; assert 400 ZOD_VALIDATION_ERROR.
