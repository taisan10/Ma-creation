CRITICALOverly Permissive CORS Whitelist with Credentials Reflection Enables Cross-Origin Refresh Token TheftSECURITY_VULNERABILITYOPEN

backend/src/app.js:56-64 · VERIFIED confidence: HIGH

Evidence

app.use(cors({
  origin: (origin, callback) => {
    if (!origin || origin.startsWith(env.clientUrl) || origin.includes('localhost') || origin.includes('pinggy') || origin.includes('trycloudflare')) {
      return callback(null, true);
    }
    return callback(new Error('Not allowed by CORS'));
  },
  credentials: true
}));

Scenario

An attacker creates a malicious page hosted on Cloudflare Quick Tunnels (*.trycloudflare.com), Pinggy, or a domain starting with env.clientUrl (e.g. https://clientUrl.attacker.com). When an authenticated user visits the attacker's page, a client-side fetch is executed to /api/auth/refresh with header 'x-refresh-token: 1'. Because origin.includes('trycloudflare') evaluates to true, CORS reflects the attacker origin with Access-Control-Allow-Credentials: true. The refreshCsrfGuard header check passes because custom headers are permitted on whitelisted CORS origins. The backend returns newly rotated accessToken and user details in the JSON response body, which the attacker script reads directly.

Impact

Complete account takeover of any logged-in web user who visits an attacker-controlled site or tunnel.

Reproduction

Deploy local server; execute fetch('http://localhost:5000/api/auth/refresh', { method: 'POST', credentials: 'include', headers: { 'Origin': 'https://evil.trycloudflare.com', 'x-refresh-token': '1' } }); verify response header Access-Control-Allow-Origin equals attacker origin and credentials allowed.

Suggested remediation

Replace substring and prefix matching (.includes, .startsWith) with a strict, exact-match array of allowed origin strings. Never allow wildcard or public tunnel domains in production CORS configuration.

Regression test

CORS preflight and actual POST requests with Origin 'https://evil.trycloudflare.com' or 'http://localhost.attacker.com' must be rejected with 403 or omitted Access-Control-Allow-Origin header.

HIGHMissing select: false on passwordHash Field in User Mongoose SchemaSECURITY_VULNERABILITYOPEN

backend/src/models/AUTH/User.js:8 · VERIFIED confidence: HIGH

Evidence

passwordHash: { type: String, required: true },

Scenario

In Mongoose, any schema path without select: false is loaded by default in every query (User.find, User.findById, User.findOne, User.findByIdAndUpdate). Although auth.service.js uses .select('+passwordHash') (demonstrating the developer intended for it to be deselected by default), omitting select: false causes passwordHash to be loaded in other services (such as payment.service.js, video.service.js, or admin endpoints) unless manually excluded with .select('-passwordHash'). Any endpoint returning a User object without manual field projection leaks the Argon2id password hash.

Impact

Exposure of Argon2id password hashes to unauthorized API consumers, logs, and external adapters, increasing risk of offline dictionary attacks.

Reproduction

Execute User.findById(id) in Node console without .select(); inspect the returned document to observe passwordHash present.

Suggested remediation

Set select: false on passwordHash in backend/src/models/AUTH/User.js and configure a toJSON schema transform to delete passwordHash upon serialization.

Regression test

Query User.findOne() without field projections and assert that returned object does not contain property 'passwordHash'.

Evidence

const existingToken = await RefreshToken.findOne({ tokenHash })
if (existingToken.isRevoked) {
  await RefreshToken.updateMany({ userId: existingToken.userId, sessionId: existingToken.sessionId }, { $set: { isRevoked: true, revokedReason: 'POSSIBLE_TOKEN_THEFT_DETECTED' } })

Suggested remediation

Use atomic findOneAndUpdate({ tokenHash, isRevoked: false }, { $set: { isRevoked: true, revokedReason: 'TOKEN_ROTATION', revokedAt: new Date() } }). Regression test

Evidence

Scenario
