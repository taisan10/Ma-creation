HIGHUnhandled ERR_HTTP_HEADERS_SENT Server Exception in SSE Endpoint When Connection Limit Is ExceededIMPLEMENTATION_DEFECTOPEN

backend/src/controllers/publicController.js:24-33 · VERIFIED confidence: HIGH

Evidence

events() in publicController.js sets res.status(200), flushes headers, and writes ': connected\n\n' BEFORE invoking addRealtimeClient(res). When clients.size >= MAX_SSE_CLIENTS (100), addRealtimeClient attempts res.status(429).json({ success: false, message: 'Too many connections' }), triggering an unhandled 'Error [ERR_HTTP_HEADERS_SENT]: Cannot set headers after they are sent to the client'.

Scenario

Under normal web traffic when 100 clients are connected to SSE, user 101 connecting triggers an uncaught ERR_HTTP_HEADERS_SENT exception. Client reconnection loops exacerbate the issue, repeatedly throwing unhandled exceptions in the Node HTTP server pipeline.

Impact

Server instability, error logging spikes, Sentry alert flooding, broken client connection state, and complete failure to communicate rate limiting to overflowing clients.

Reproduction

Simulate 100 concurrent SSE connections to /api/public/events. On the 101st request, observe the Node.js server throw ERR_HTTP_HEADERS_SENT when attempting to set status 429.

Suggested remediation

Check capacity (clients.size >= MAX_SSE_CLIENTS) in events() BEFORE setting HTTP 200 headers. If at capacity, immediately return res.status(429).json(...) before stream headers are written. In routes/public.js, wrap events in asyncHandler, and in middleware/error.js ensure res.headersSent is checked before attempting error serialization.

Regression test

Mock clients.size = 100 and issue a GET request to /api/public/events. Assert response status is 429 and no ERR_HTTP_HEADERS_SENT exception is thrown.

HIGHComplete Denial of Realtime Updates via Global Rate Limit Bypass and Uncapped Per-IP SSE ConnectionsSECURITY_DOSOPEN

backend/src/app.js:79-84 · VERIFIED confidence: HIGH

Evidence

In backend/src/app.js, express-rate-limit explicitly skips /api/public/events via skip: (req) => ... req.path === '/api/public/events'. There is no per-IP connection limit, no IP-based rate limiting on /api/public/events, and no authentication required.

Scenario

An unauthenticated remote attacker or misconfigured client opens 100 parallel EventSource connections from a single IP. All 100 connections are accepted and occupy every slot up to MAX_SSE_CLIENTS = 100.

Impact

Total denial of service for the realtime update subsystem. Every other user across the entire platform is blocked from receiving live CMS updates, and any new visitor triggers the ERR_HTTP_HEADERS_SENT exception.

Reproduction

Script 100 concurrent GET requests from a single client IP to /api/public/events. All 100 are accepted without rate limiting, holding all server SSE slots.

Suggested remediation

Implement per-IP connection limits (e.g., maximum 3-5 concurrent SSE connections per client IP) and apply a dedicated rate limiter (e.g., max 10 connection attempts per 5 minutes) on /api/public/events.

Regression test

Attempt 6 concurrent SSE connections from a single IP address. Assert that connections exceeding the per-IP threshold are rejected with HTTP 429.

MEDIUMSocket and File Descriptor Leak Due to Missing res.end() on SSE Lifetime ExpirationRESOURCE_LEAKOPEN

backend/src/services/realtime.js:16-24 · VERIFIED confidence: HIGH

Evidence

In realtime.js, const cleanup = () => { clearInterval(heartbeat); clearTimeout(lifetime); clients.delete(res); }. When the 1-hour MAX_SSE_LIFETIME_MS timeout triggers, cleanup() removes the client from clients and clears timers, but never calls res.end() or destroys the socket.

Scenario

When long-running clients remain connected past 1 hour, heartbeats cease, but the underlying TCP connection and Node response stream remain open indefinitely in memory.

Impact

Gradual socket, memory, and file descriptor leakage on the server, eventually degrading OS network resources.

Reproduction

Temporarily set MAX_SSE_LIFETIME_MS to 1000ms. Open an SSE connection. After 1s, verify client is removed from clients set, but the TCP socket remains in ESTABLISHED state without FIN packet being sent.

Suggested remediation

In cleanup(), explicitly call if (!res.writableEnded) { res.end(); } to terminate the HTTP response stream when lifetime expires.

Regression test

Trigger the lifetime expiration timer and assert that res.writableEnded becomes true and socket terminates.
