backend/src/routes/leads.js:19 · VERIFIED confidence: HIGH

Evidence

router.post('/', leadRateLimit, validate(createLeadSchema), asyncHandler(c.createLead)) — endpoint is open without CAPTCHA, honeypot, or proof-of-work challenge.

Scenario

An attacker or botnet automates requests to POST /api/leads with randomized phone numbers and messages. Without CAPTCHA or bot verification, the backend inserts every request into MongoDB, polluting CRM/leads records and exhausting system resources.

Impact

Marketing queue pollution, database storage bloat, disruption of sales operations, and potential downstream SMS/email notification quota depletion.

Regression test

Verify POST /api/leads rejects submissions with missing or invalid CAPTCHA tokens with HTTP 400/403, and rejects requests with filled honeypot fields.

MEDIUMIn-Memory Rate Limiting Allows Multi-Instance Bypass and Lacks Distributed StoreSECURITY_DEFECTOPEN

backend/src/routes/leads.js:11-17 · VERIFIED confidence: HIGH

Evidence

const leadRateLimit = rateLimit({ windowMs: 15 * 60 * 1000, max: 10, standardHeaders: 'draft-8', legacyHeaders: false, message: { success: false, message: 'Too many requests, please try again later' } })

Scenario

In a clustered, multi-container or PM2 deployment, memory stores are isolated per Node process. Requests hitting different worker instances do not share rate limit counters. Furthermore, application restarts immediately wipe counters.

Impact

Attackers can bypass the 10 requests per 15 minutes limit by rotating across cluster workers or triggering container restarts.

Reproduction

Deploy across multiple worker processes or restart the backend process; rate limit counters reset immediately.

Suggested remediation

Configure express-rate-limit with rate-limit-redis using the project's existing ioredis client.

Regression test

Assert rate limit enforcement persists across worker restarts and cluster nodes using Redis as the centralized counter.

HIGHMissing Database Index on createdAt and status Causes In-Memory Sort and Full Collection ScansPERFORMANCE_RELIABILITYOPEN

backend/src/models/CMS/Lead.js:2 · VERIFIED confidence: HIGH

Evidence

Schema defines { timestamps: true } but no index on createdAt or status. Lead.find().sort({ createdAt: -1 }) executes without an index.

Scenario

Admin dashboard and lead listings run Lead.find().sort({ createdAt: -1 }).limit(limit). Without an index on createdAt, MongoDB must perform a COLLSCAN and an in-memory sort. Once lead records grow, MongoDB will throw an error exceeding the 32MB in-memory sort threshold.

Impact

Query latency spikes, high database CPU utilization, and 500 crashes when collection data exceeds 32MB during in-memory sort.

Reproduction

Seed 10,000 lead records and execute query explain plan: stages reveal COLLSCAN and SORT without IXSCAN.

Suggested remediation

Add schema.index({ createdAt: -1 }) and schema.index({ status: 1, createdAt: -1 }) in backend/src/models/CMS/Lead.js and backend/src/scripts/ensure-indexes.js.

Regression test

Execute explain plan on Lead.find().sort({ createdAt: -1 }) and assert IXSCAN is utilized with zero COLLSCAN.
