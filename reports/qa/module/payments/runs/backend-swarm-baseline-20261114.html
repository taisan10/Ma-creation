CRITICALTOCTOU Concurrency Race Condition in Order Creation Leading to Duplicate Charging and Double SpendSECURITY_VULNERABILITYOPEN

backend/src/services/payment.service.js:46-71 · VERIFIED confidence: HIGH

Evidence

createOrder queries: Payment.findOne({ plan: plan._id, status: 'paid', user: userId }). It checks only for 'paid', ignoring existing pending ('created') orders. receipt is generated as `mac_${Date.now()}`, which bypasses Razorpay DUPLICATE_ORDER deduplication. No distributed lock or unique DB index exists.

Scenario

A student double-clicks 'Buy Now' or submits concurrent automated order creation requests. Both requests find no 'paid' record, generate distinct `mac_${Date.now()}` receipts, and create two distinct Razorpay orders. The student's card/UPI is debited twice for the same plan, creating two separate 'paid' records in MongoDB with duplicate charges.

Impact

Direct customer financial loss, dispute and chargeback liabilities, and corrupt payment accounting.

Reproduction

Send 2 concurrent POST /api/payments/order requests with identical { planId } and Bearer token; both succeed with HTTP 201 and create two active Razorpay orders.

Suggested remediation

1. Check for active 'created' orders within a 30-minute lock window before creating an order. 2. Use deterministic receipt key: `mac_${userId}_${planId}` so Razorpay returns DUPLICATE_ORDER on concurrent calls. 3. Acquire a distributed lock on Redis key `lock:payment:order:${userId}:${planId}`.

Regression test

Execute 10 concurrent POST /api/payments/order requests for the same user and plan; assert exactly 1 returns 201 and 9 return 409 Conflict.

HIGHUnhandled Buffer Length Mismatch in Webhook HMAC Verification Causes Uncaught Exception / DoSSECURITY_VULNERABILITYOPEN

backend/src/services/payment.service.js:204-213 · VERIFIED confidence: HIGH

Evidence

handleWebhook computes `expected` (64-char hex string) and evaluates: if (expected.length !== signature.length || !crypto.timingSafeEqual(Buffer.from(expected), Buffer.from(signature))). It compares string character length instead of byte length. If an attacker submits a 64-char multi-byte UTF-8 string (e.g. 64 double-byte chars = 128 bytes), the character length check passes, and crypto.timingSafeEqual throws an unhandled RangeError [ERR_CRYPTO_TIMING_SAFE_EQUAL_LENGTH].

Scenario

An external attacker sends POST /api/payments/webhook with header `x-razorpay-signature` consisting of 64 two-byte UTF-8 characters. The endpoint crashes with an uncaught RangeError, causing an unhandled 500 error and webhook processing pipeline failure.

Impact

Denial of Service on payment webhook handler, unhandled error logging, and service degradation.

Reproduction

Send POST /api/payments/webhook with header `x-razorpay-signature: \u00e9...` (64 characters) and body `{}`; observe unhandled RangeError crash.

Suggested remediation

Validate signature format with regex `/^[0-9a-fA-F]{64}$/`. Parse both strings into hex buffers: `const expBuf = Buffer.from(expected, 'hex'); const sigBuf = Buffer.from(signature, 'hex'); if (expBuf.length !== sigBuf.length || !crypto.timingSafeEqual(expBuf, sigBuf)) throw new AppError('Invalid webhook signature', 400);`

Regression test

Submit webhook with 64-char multi-byte UTF-8 signature; assert HTTP 400 Bad Request returned cleanly without throwing RangeError.

HIGHComplete Absence of Amount and Currency Verification During Payment Verification and Webhook CaptureSECURITY_VULNERABILITYOPEN

backend/src/services/payment.service.js:110-224 · VERIFIED confidence: HIGH

Evidence

verifyPayment only verifies HMAC of `orderId|paymentId` and never calls Razorpay API to confirm captured amount or currency. handleWebhook extracts `entity = req.body?.payload?.payment?.entity` and marks payment 'paid' without verifying `entity.amount === Math.round(payment.amount * 100)` or `entity.currency === payment.currency`.

Scenario

If a transaction is partially captured, paid in an unauthorized currency, or if gateway amounts desynchronize, the backend blindly marks the plan as fully paid without verifying that the captured amount matches the required plan price.

Impact

Financial leakage, underpayment vulnerabilities, and inability to reconcile financial accounting records.

Reproduction

Trace verifyPayment and handleWebhook; note that neither method inspects or compares `amount` or `currency` against `payment.amount`.

Suggested remediation

In handleWebhook: verify `entity.amount === Math.round(payment.amount * 100)` and `entity.currency === payment.currency` before setting status 'paid'. In verifyPayment: fetch payment details via `getRazorpayClient().payments.fetch(razorpayPaymentId)` and assert `amount` and `status === 'captured'`.

Regression test

Send webhook with `entity.amount` differing from `payment.amount * 100`; assert payment status is NOT changed to 'paid' and error is logged.

HIGHPermanent Lifetime Entitlement Granted Without Subscription/Plan Duration Expiration or RevocationSECURITY_VULNERABILITYOPEN

backend/src/middleware/requireEntitlement.js:13-44 · VERIFIED confidence: HIGH

Evidence

Ownership is checked via: Payment.exists({ user: req.user.sub, plan: course.plan, status: 'paid' }). The Payment schema contains no `expiresAt`, `validUntil`, or `isRevoked` fields. Plans with `billing` and `duration` (e.g. 1 month retainer) grant permanent, perpetual access with no expiration or revocation mechanism.

Scenario

A customer purchases a 30-day course or 1-month retainer plan. After 30 days, 1 year, or indefinitely, the customer retains full DRM video and course streaming access because Payment.exists always returns true.

Impact

Severe revenue leakage, inability to offer recurring subscriptions or time-limited access, and breach of retainer service agreements.

Reproduction

Create plan with duration '30 days'. Pay for plan. Simulate 60 days passing; send GET /api/videos/:id/hls; entitlement is still granted.

Suggested remediation

Add `expiresAt: Date` and `isRevoked: Boolean` to Payment schema. Populate `expiresAt` upon order completion based on `plan.duration`. Update requireEntitlement to require `{ user: req.user.sub, plan: course.plan, status: 'paid', isRevoked: { $ne: true }, $or: [{ expiresAt: null }, { expiresAt: { $gt: new Date() } }] }`.

Regression test

Verify access for payment with `expiresAt` set to past timestamp returns HTTP 403 NOT_ENTITLED.
